Package reference

Kairo Package Atlas

Kairo is a retrieval-native temporal engine for agents and evolving knowledge graphs. It ships as fourteen independent packages on a strict dependency DAG — install the three you need, or the whole stack.

Install

Every package is versioned and released separately. Nothing imports upward, so a package never drags the stack in behind it. The smallest useful install is retrieval over local files:

# lexical retrieval over PDFs, CSVs, and docs
pip install kairo-core kairo-ingest kairo-retrieval

# add graph construction and versioned history
pip install kairo-graph kairo-temporal

# the full engine — agents, 3-layer RAG, connectors
pip install kairo-agents kairo-rag kairo-connectors

For local development across the monorepo, install each package in editable mode from its own directory:

pip install -e core -e embeddings -e ingest -e graph \
            -e retrieval -e temporal -e agents -e rag

Quickstart

Three lines to a working retrieval loop. LocalPipeline runs BM25 over tokens, persists to a JSON store, and returns evidence with scores and provenance.

from pathlib import Path
from kairo_core import QueryRequest
from kairo_retrieval import LocalPipeline

pipeline = LocalPipeline(store_path=Path("kairo_store.json"))
pipeline.ingest_paths([Path("handbook.pdf"), Path("policies.csv")])

response = pipeline.query(QueryRequest(query="What is the refund window?", top_k=5))
print(response.answer)
for ev in response.evidences:
    print(ev.document_id, round(ev.score, 3))

Add an embedding provider and retrieval becomes hybrid — BM25 and cosine similarity fused by Reciprocal Rank Fusion at k=60:

from kairo_embeddings import get_provider

pipeline = LocalPipeline(
    store_path=Path("kairo_store.json"),
    embedding_provider=get_provider(),   # resolves the default backend
    hop_decay=0.5,                       # graph-walk score decay per hop
)

On the hash-stub provider. With no embedding_provider, the pipeline stays BM25-only by design. The built-in hash stub carries no semantic signal and is never used as a similarity proxy — it exists for deterministic tests.

Dependency map

The layering is enforced, not conventional: kairo-core depends on nothing but Pydantic, and each tier may only import from tiers below it. This is what makes a partial install coherent.

kairo-core

tier 0

Every shared type in the system. It depends only on Pydantic, so any package can import it without pulling in numpy, pandas, or networkx. Data contracts live here even when the implementation lives elsewhere — AnalyticsPlan is defined in core, but only kairo-analytics touches pandas.

kairo-embeddings

tier 1

A provider registry and a numpy-backed store with cosine top-k. Providers register by name, so swapping sentence-transformers for Ollama or a hosted API is a config change, never a code change.

Depends

Exports

print(available_providers())      # ['hash', 'sentence-transformers', ...]

store = EmbeddingStore(provider.dim)
store.add_many((d.id, provider.embed(d.text)) for d in docs)

for node_id, score in store.similar(provider.embed("refunds"), k=5):
    print(node_id, round(score, 3))

store.save("matrix.npy", "index.json")

kairo-graph

tier 2

Graph construction and the 3-layer decomposition. KairoGraph wraps a NetworkX DiGraph behind a narrow interface so the backing store can become Kuzu or Memgraph later without touching call sites. Deterministic SHA-256 hashing is what lets kairo-temporal skip writing a snapshot when nothing changed.

Depends
kairo-core · kairo-embeddings · networkx
Exports
KairoGraph · LayeredKairoGraph · GraphBuilder · LayeredGraphBuilder · DocumentGraphBuilder · DocumentLayeredBuilder · LLMExtractedGraphBuilder · ExtractorProvider · OllamaExtractor · detect_communities · add_concept_nodes · summarize_community · edge_attrs · save_graph · load_graph

The three layers are document (sections, headings, files), semantic (concepts and themes), and detail (data points and evidence). Edges within a layer are GraphEdge; edges between layers are InterLayerEdge, so traversal can tell "going deeper" from "going sideways".

from kairo_graph import DocumentLayeredBuilder, detect_communities, add_concept_nodes

graph = DocumentLayeredBuilder().build(docs)
print(graph.hash())              # stable content address

communities = detect_communities(graph)   # Leiden, if igraph is installed
add_concept_nodes(graph, communities)

Every edge carries a provenance tag — structural, extracted, inferred, or ambiguous — so a citation can distinguish a heading hierarchy from an LLM's guess.

kairo-retrieval

tier 2

The retrieval layer: a local pipeline with persistence and a thin HTTP client for a hosted deployment. Ranking is BM25 fused with cosine similarity via Reciprocal Rank Fusion, then boosted along graph edges with a per-hop decay.

Depends
kairo-core · kairo-embeddings · rank-bm25 · numpy
Exports
LocalPipeline · HostedClient
from kairo_core import QueryRequest
from kairo_retrieval import LocalPipeline, HostedClient

local = LocalPipeline(
    store_path="kairo_store.json",
    embedding_provider=provider,
    graph_neighbors=graph.neighbors,   # optional graph-walk boost
    hop_decay=0.5,
)
result = local.query(QueryRequest(query="refund window", top_k=5,
                                filters={"source": "handbook.pdf"}))

hosted = HostedClient(base_url="https://api.example.com", api_key=key)

kairo-temporal

tier 3

Git-shaped version control for knowledge graphs. A .kairo/ directory holds HEAD, branch refs, a history DAG, and one directory per snapshot containing the graph and its embeddings. Branching is native — Snapshot.parents is a list, so merges and forks are schema-level, not a later migration.

Depends
kairo-core · kairo-graph · kairo-embeddings
Exports
KairoStore · SnapshotBuilder · HistoryGraph · HistoryWalker · diff_graphs · snapshot_id_from_hash
from kairo_temporal import KairoStore, SnapshotBuilder, diff_graphs

store = KairoStore.init(".", history_graph_id="handbook")
builder = SnapshotBuilder(history_graph_id="handbook", builder_name="layered")

snap = builder.build(graph, message="Q3 policy import")
store.commit(snap, graph, embeddings)      # advances the current branch

# branch, then reconstruct a past state
store.set_branch("experiment", snap.id)
store.checkout_branch("experiment")
old_snap, old_graph, old_emb = store.rollback(prior_id)

print(diff_graphs(old_graph, graph).added_nodes)

The .kairo/ layout on disk:

.kairo/
├── HEAD                      # "ref: refs/branches/main", or a bare id when detached
├── refs/branches/<name>
├── history.json              # the snapshot DAG
└── snapshots/<snapshot_id>/
    ├── snapshot.json
    ├── graph.json
    └── embeddings/{matrix.npy, index.json}

kairo-rag

tier 3

Where retrieval, graphs, and agents meet. TemporalRAGEngine builds a 3-layer graph, embeds each layer separately, runs KNN seeding plus BFS expansion, and snapshots the result into a session so follow-up queries reuse the graph instead of rebuilding it.

Depends
kairo-core · kairo-graph · kairo-embeddings · kairo-retrieval · kairo-agents
Exports
TemporalRAGEngine · RAGResult · MultiAgentOrchestrator · SessionStore · GraphSnapshot · LayerEmbeddingStore · EngineRunner · EngineResult · AgentFinding · WebEnricher · CitationVerifier · graph_walk · knn_search · cluster_visited_nodes
from kairo_embeddings import get_provider
from kairo_rag import TemporalRAGEngine, CitationVerifier

engine = TemporalRAGEngine(
    get_provider(),
    top_k=5,                 # nearest neighbours per layer
    walk_depth=2,             # BFS hops from each seed
    max_nodes_per_layer=30,   # expansion budget
)

result = engine.query("How did the refund policy change?", docs,
                      session_id="user-42", reuse_snapshot=True)

print(result.trace.visited_nodes)    # drives the 3D visualisation
report = CitationVerifier().verify(result.answer, result.evidences)

The TraversalTrace on every result records each visit, expansion, and layer crossing — it is both the audit trail and the data source for the frontend graph view.

The bitemporal model

Kairo today versions the graph the way git versions a tree: each snapshot records when it was committed. That answers "what did the graph look like on Tuesday?" — one axis of time.

A bitemporal engine carries two independent axes on every fact, and the second one is what makes corrections and audits possible:

valid time

When the fact was true in the world. The refund window was 30 days from January through June.

transaction time

When Kairo came to believe it. We recorded that window in September, after a late document import.

With both axes, a fact becomes an assertion over two intervals, and retraction means closing a transaction interval rather than deleting a row:

class Interval(BaseModel):
    start: datetime
    end: Optional[datetime] = None        # None = still open

class TemporalFact(BaseModel):
    valid: Interval    # when it was true in the world
    tx: Interval       # when Kairo believed it
QuestionAxes neededAvailable today
What does the graph say now?—Yes
What did the graph look like on Tuesday?txYes — snapshots
What was true in January?validNot yet
What did we believe in March about January?valid × txNot yet
Re-answer a past question with today's knowledgevalid × txNot yet

Status. The two-axis model is the current design direction, not shipped API. Snapshot.timestamp in kairo-core is transaction time only, and it sits on the snapshot rather than on individual nodes and edges. Treat this section as the roadmap it is.

Recipes

Versioned RAG over a changing corpus

Build a layered graph, commit it, answer from it, then commit again when the corpus changes and diff the two.

from kairo_embeddings import get_provider
from kairo_graph import DocumentLayeredBuilder
from kairo_ingest import ingest_any
from kairo_rag import TemporalRAGEngine
from kairo_temporal import KairoStore, SnapshotBuilder, diff_graphs

provider = get_provider()
store = KairoStore.init(".", history_graph_id="corpus")
snapper = SnapshotBuilder(history_graph_id="corpus", builder_name="layered")
engine = TemporalRAGEngine(provider)

docs = ingest_any(Path("handbook_v1.pdf"))
graph = DocumentLayeredBuilder().build(docs)
v1 = snapper.build(graph, message="v1 import")
store.commit(v1, graph)

answer = engine.query_from_graph("refund window", graph)

# ... corpus changes ...
docs2 = ingest_any(Path("handbook_v2.pdf"))
graph2 = DocumentLayeredBuilder().build(docs2)
v2 = snapper.build(graph2, parents=[v1.id], message="v2 import")
store.commit(v2, graph2)

delta = diff_graphs(graph, graph2)
print(delta.added_nodes, delta.removed_nodes, delta.changed_nodes)

Bring your own embedding backend

from kairo_embeddings import register_provider, get_provider

class MyProvider:
    dim = 1024
    def embed(self, text: str):
        return my_client.encode(text)

register_provider("mine", MyProvider)
provider = get_provider("mine")

Retrieval that follows graph edges

Pass a neighbour function into the pipeline and lexical hits propagate score to their graph neighbours, decayed per hop.

pipeline = LocalPipeline(
    store_path="store.json",
    embedding_provider=provider,
    graph_neighbors=lambda node_id: graph.neighbors(node_id),
    hop_decay=0.5,      # a 2-hop neighbour keeps 25% of the seed's score
)
